# DroidVNA 0.7.2-beta

> [中文版](../../release-notes/0.7.2-beta.md)

This release is a **protocol and calibration reliability fix** with no new features. Two main threads:

1. The `SweepSettings` sent to a Harogic B60 must include the 32nd byte, `extTrigger`. Otherwise the device keeps the stale value a previous packet left in its receive buffer, starts waiting for triggers, and looks hung.
2. The E-Cal capture timeout can no longer be a fixed 8 seconds. At a low IFBW such as 15 Hz a single complete sweep takes far longer than that, so a healthy device reported "port X has no scan data".

## Fixes

### B60 protocol: send the `extTrigger` extension byte

The VNB-60's `SweepSettings` is **32 bytes** (31 upstream), ending with `extTrigger`
(`0` = free-running continuous sweep, non-zero = wait for that many external trigger events per point). The firmware decodes into a **shared, reused** receive buffer and only overwrites the bytes actually received, so a 31-byte packet leaves this byte holding whatever a previous packet put there:

| Residue | Behaviour |
| --- | --- |
| `0` | Normal continuous sweep |
| `1` | Only about 11 points |
| `0xFF` | No data at all — looks like a dead device |

The app now **always sends the complete 32 bytes** with `extTrigger` explicitly 0. The layout is pinned by `Protocol.SweepSettings` and unit tests, and the new complete `packet type` table keeps type numbers from being renumbered by accident.

### The "SA → VNA reset" workaround is gone

Older builds sent an SA configuration before every sweep configuration. That only helped because the mode switch happened to overwrite that area of the buffer, which is why it failed intermittently (a random "success, success, failure" cycle that re-sending the settings did not fix) and why it added more than 0.8 s to every configuration. Now, if a configuration is ACKed but produces no usable datapoint within 6 seconds, the app **re-sends the same configuration** (up to twice) instead of switching modes.

### E-Cal capture timeouts scale with the sweep time

- The timeout is about **two sweep periods** (8 s floor, 20 min cap). The period comes from points and IFBW, and a measured sweep duration on the same grid wins over the estimate (the B60's per-point cost is not a pure function of IFBW).
- Slow sweeps are **not waited for twice**: a second sweep is only awaited when the first arrived within one second (and may be a leftover from before the standard switch).
- Progress is shown every second, e.g. "Port 1 OPEN · 286/401 points captured…", for THRU and isolation too.
- Manual SOL captures use the same timeout.

### `DeviceStatus` (VD0) decoding

`supply_current` used to be permanently null because its size guard was written as `>= 7` while the B60's VD0 frame is only 6 bytes; its unit is mA. The `FPGA_configured` / `extRefAvailable` bits are decoded too, and the device page now shows an FPGA status lamp and the supply current.

## Reserved: external triggering

External triggering is **not implemented**: the `extTrigger` byte, the `SetTrigger` (28) / `ClearTrigger` (29) packet numbers and `syncMode = 3` (trigger synchronization) are reserved and documented in the protocol structures. Harogic has not defined what non-zero values mean (255 produced no output at all), so the app always sends 0.

## Verification

- **77 JVM unit tests pass** (10 new: 32-byte `SweepSettings` layout and the reserved `extTrigger`, the full packet-type table, `VD0` decoding, stage-word packing, trigger reservation staying off, impossible frame lengths being skipped, slow-sweep timeout scaling with bounds, no double wait for slow sweeps, and a measured sweep duration winning over the estimate).
- **Hardware** (Xiaomi Pad, Android 17 + B60 FW 1.8.6 + ECB-60 FW 0.3.2):
  - Continuous sweeping works: 401 points at 3 kHz measured about 3.0 sweeps/s, the log shows `SweepSettings(… extTrigger 0)`, and 15 Hz / 2001 points keeps producing points.
  - **E-Cal at low IFBW**: 401 points at **15 Hz** (about 30 s per sweep, far beyond the old 8 s timeout) completed a full 12-term SOLT **in one run** — about 7 minutes, 7 captures, with per-second progress; 401 points at 100 Hz took about 1.5 minutes. Before the fix the same 15 Hz settings always failed the first capture with "port X has no scan data".
- **Not yet verified**: DTF distance accuracy against a real cable, manual SOLT on hardware, LibreVNA's own hardware.

## Upgrade notes

- The protocol is still **v14**; no firmware upgrade is needed.
- The calibration data format is unchanged; saved calibrations keep working.
- The same signing key installs over the previous version; `versionCode` goes from 10 to 11.
